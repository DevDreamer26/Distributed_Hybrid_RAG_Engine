A production-grade, distributed Retrieval-Augmented Generation (RAG) platform built with **FastAPI**, **Celery**, **PostgreSQL (`pgvector` + `tsvector`)**, **FlashRank**, and **Groq LPUs**.

This system addresses common bottlenecks in naive RAG pipelines, such as event-loop starvation during parsing, semantic blind spots in pure dense retrieval, and bi-encoder scoring inaccuracy. It combines **asynchronous ingestion**, **two-stage hybrid search with Reciprocal Rank Fusion (RRF)**, **deep cross-encoder re-ranking**, and **grounded generation with chunk-level attribution**.

## Key Engineering Highlights

### 1. Asynchronous Event-Driven Ingestion

- **Non-Blocking Ingestion:** Document uploads return an immediate `HTTP 202 Accepted` response with an ingestion tracking UUID.
- **Worker Isolation:** Heavy PDF text extraction, sliding-window chunking (`chunk_size=300`, `chunk_overlap=50`), and batch embedding computations are offloaded to **Celery workers** over a **Redis** message queue.
- **Failure Safety:** Database updates run within explicit session boundaries, rolling back cleanly and marking the document `FAILED` if errors occur mid-stream.

### 2. Multi-Modal Two-Stage Retrieval

- **Branch A (Dense Semantic Retrieval):** Uses `pgvector` to run cosine distance scans (`<=>`) over 384-dimensional dense vectors generated by `all-MiniLM-L6-v2`.
- **Branch B (Sparse Lexical Retrieval):** Uses PostgreSQL native `tsvector` with `ts_rank_cd` to execute cover-density keyword matching for exact IDs, technical terms, and code snippets.
- **Reciprocal Rank Fusion (RRF):** Merges dense and sparse outputs using positional rankings rather than unstable, uncalibrated score weights:

  $$RRF\_Score(d) = \sum_{m \in \{\text{dense}, \text{sparse}\}} \frac{1}{k + \text{rank}_m(d)} \quad (k = 60)$$

- **Cross-Encoder Re-Ranking:** The top 10 RRF candidates pass through `flashrank` (`ms-marco-MiniLM-L-12-v2`). The model scores full query-document token interactions simultaneously via self-attention, pruning false positives before the context hits the LLM.

### 3. Sub-Second Grounded Synthesis

- **Ultra-Low Latency:** Feeds the top 3 cross-encoder re-ranked chunks to Groq's LPU infrastructure running `llama-3.3-70b-versatile`.
- **Strict Context Boundary:** Enforces a system prompt that mandates direct source citations (`[Source Chunk X]`) and suppresses hallucinations.

## Local Setup

### 1. Prerequisites

Make sure the following are installed:

- Docker & Docker Compose
- Python 3.11+
- Node.js v18+ and npm
- A free [Groq Cloud](https://console.groq.com/) API key

### 2. Infrastructure Setup (Docker Compose)

Start the PostgreSQL container (with `pgvector` enabled) and the Redis broker from the project root:

```bash
docker compose up -d
```

Verify the containers are running:

```bash
docker ps
```

| Service | Address |
|---|---|
| PostgreSQL | `localhost:5435` |
| Redis | `localhost:6379` |

### 3. Backend Setup

**a. Create and activate a virtual environment**

```bash
cd backend
python -m venv .venv
source .venv/bin/activate    # On Windows: .venv\Scripts\activate
```

**b. Install dependencies**

```bash
pip install --upgrade pip
pip install -r requirements.txt
```

**c. Configure environment variables**

Create a `.env` file in the `backend/` directory:

```env
# PostgreSQL Connection Strings
DATABASE_URL=postgresql+asyncpg://rag_user:rag_password@localhost:5435/rag_engine
SYNC_DATABASE_URL=postgresql+psycopg://rag_user:rag_password@localhost:5435/rag_engine

# Redis Configuration
REDIS_URL=redis://localhost:6379/0

# Vector Settings
VECTOR_DIMENSION=384

# Groq Cloud API
GROQ_API_KEY=gsk_your_actual_groq_api_key_here
GROQ_MODEL=llama-3.3-70b-versatile
```

**d. Start the Celery background worker**

Open a dedicated terminal, navigate to `backend/`, activate your `.venv`, and run:

```bash
celery -A app.workers.celery_worker.celery_app worker --loglevel=info
```

**e. Start the FastAPI gateway**

Open a separate terminal, navigate to `backend/`, activate your `.venv`, and run:

```bash
uvicorn app.main:app --reload --port 8000
```

Interactive API documentation is available at [http://localhost:8000/docs](http://localhost:8000/docs).

### 4. Frontend Setup

**a. Install dependencies**

```bash
cd frontend
npm install
```

**b. Configure environment variables**

Create a `.env` file in the `frontend/` directory:

```env
VITE_API_BASE=http://localhost:8000/api/v1
```

**c. Start the Vite development server**

```bash
npm run dev
```

Open your browser at [http://localhost:5173](http://localhost:5173).

> **Tip:** You need three processes running at the same time: the Celery worker, the FastAPI server, and the Vite dev server. Docker must also be up for PostgreSQL and Redis.

## Architectural Decisions & Trade-Offs

### 1. PostgreSQL + pgvector vs. Standalone Vector Databases

- **Atomic Consistency:** Using PostgreSQL as both the relational and vector store allows cascading deletes (`ON DELETE CASCADE`). Deleting a document atomically purges its metadata, raw text, embeddings, and inverted indexes inside a single ACID transaction, preventing orphaned vectors.
- **Operational Simplicity:** Avoids managing external synchronization pipelines, network overhead, and separate access controls for external vector databases (e.g., Pinecone or Milvus).

### 2. Reciprocal Rank Fusion (RRF) vs. Linear Score Blending

- **Unbounded Score Variance:** Cosine distance is strictly bounded ($[0, 2]$), whereas BM25 / `ts_rank_cd` scores are unbounded ($[0, \infty)$) and change based on document collection size.
- **Scale-Invariance:** RRF scores candidates purely by their relative rank order, making it stable across diverse document types without manual weight tuning.

### 3. Two-Stage Retrieval (Bi-Encoder + Cross-Encoder)

- **Performance:** Running cross-attention across thousands of chunks introduces severe latency bottlenecks. A bi-encoder (`all-MiniLM-L6-v2`) handles initial candidate retrieval across the entire database in under 20 ms, while the cross-encoder (`flashrank`) evaluates only the top 10 candidates with full token-to-token attention.
